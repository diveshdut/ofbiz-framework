# OFBIZ-13451 Design: Apply Supplier Lead Time To Purchased MRP Requirements

## Summary

`OFBIZ-13451` addresses a gap in MRP scheduling for procured items. Today, proposed purchase requirements are created with `requirementStartDate` equal to `requiredByDate`, so MRP does not indicate when a purchase should be initiated to satisfy supplier lead time.

This change will make purchased MRP requirements use `SupplierProduct.standardLeadTimeDays` when available on an active supplier record. When lead time is available, MRP will back-schedule `requirementStartDate` from `requiredByDate` by that supplier lead time. When no applicable supplier lead time exists, MRP will preserve current behavior and leave `requirementStartDate = requiredByDate`.

## Scope

This design is limited to purchased-item procurement lead time in MRP.

Included:

- Resolve supplier lead time for purchased MRP requirements from active `SupplierProduct` rows.
- Prefer an active primary supplier when determining lead time.
- Fall back to any other active supplier with a defined `standardLeadTimeDays` when no active primary supplier with lead time exists.
- Preserve current behavior when no active supplier lead time can be resolved.

Excluded:

- No change to built-versus-bought classification in MRP.
- No use of `ProductFacility.daysToShip` as a procurement fallback.
- No supplier-calendar or facility-calendar enhancement work.
- No changes for `OFBIZ-13452`, which should remain a separate improvement.
- No UI, entity-model, or service-contract expansion for this ticket.
- No automated test additions for this change.

## Current Behavior

The purchased-item path in MRP currently receives no procurement lead-time offset in the shortage planning flow. As a result, the proposed `PRODUCT_REQUIREMENT` start date for purchased items is effectively created at the same point as the required-by date.

Manufactured items already use their existing routing-based back-scheduling logic and are not part of this problem.

## Desired Behavior

When MRP creates a proposed `PRODUCT_REQUIREMENT` for a purchased item:

1. Resolve an active supplier for the product that can provide lead time.
2. Use that supplier's `standardLeadTimeDays` to back-schedule `requirementStartDate` from `requiredByDate`.
3. If no active supplier lead time is found, keep `requirementStartDate = requiredByDate`.

This preserves backward compatibility for products without maintained supplier lead time while improving scheduling accuracy for products that do have the data configured.

## Supplier Selection Rules

Supplier resolution must only consider active `SupplierProduct` rows effective for the requirement date. Expired or otherwise inactive supplier rows must not be used.

The selection precedence is:

1. Any active primary supplier with a defined `standardLeadTimeDays`.
2. Any other active supplier with a defined `standardLeadTimeDays`.
3. No supplier lead time found, so preserve existing behavior.

If multiple active primary suppliers exist, any one of them is acceptable for this ticket. This design does not introduce additional supplier ranking logic beyond the precedence above.

## Architecture

The change should stay within the existing MRP shortage-planning flow in the manufacturing component.

Recommended structure:

- Keep bought-versus-built determination unchanged in `MrpServices`.
- Add a small helper in the MRP code path to resolve supplier lead time for purchased items.
- Pass the resolved lead-time value into the existing purchased-item start-date calculation path.
- Continue using the existing manufactured-item routing logic without modification.

This keeps the behavior change narrow and avoids mixing procurement lead-time logic into unrelated MRP classification or routing behavior.

## Data Flow

For a purchased proposed order:

1. MRP detects a shortage and creates a `ProposedOrder`.
2. Before calculating the purchased-item start date, MRP resolves supplier lead time from `SupplierProduct`.
3. The lookup filters supplier rows by product and effective date.
4. The lookup prefers an active primary supplier with `standardLeadTimeDays`.
5. If no active primary supplier with lead time exists, the lookup falls back to any active supplier with `standardLeadTimeDays`.
6. The resolved lead time is used to calculate `requirementStartDate`.
7. If no lead time is resolved, `requirementStartDate` remains equal to `requiredByDate`.

## Error Handling And Fallbacks

Missing supplier configuration is not an MRP error for this ticket. If no active supplier lead time is available, MRP should quietly preserve the current date behavior.

Actual entity or service failures encountered while reading supplier data should continue to follow existing OFBiz error handling and logging patterns used in the surrounding MRP code.

## Manual Verification

Manual verification should cover the following cases:

1. Purchased item with an active primary supplier and defined `standardLeadTimeDays`:
   `requirementStartDate` is earlier than `requiredByDate` by the supplier lead time.
2. Purchased item with multiple suppliers where the active primary supplier has lead time:
   the primary supplier's lead time is used.
3. Purchased item with no active primary supplier lead time but another active supplier has lead time:
   the non-primary active supplier lead time is used.
4. Purchased item with only expired supplier rows or no defined active lead time:
   `requirementStartDate` remains equal to `requiredByDate`.

## Non-Goals

This ticket will not:

- Change the logic that determines whether MRP proposes a purchase requirement or an internal requirement.
- Reinterpret `ProductFacility.daysToShip` as procurement lead time.
- Introduce supplier-specific calendar scheduling.
- Introduce facility-calendar scheduling.
- Add new entities, seed data, screens, forms, or labels.

## Related Work

- `OFBIZ-13451`: procurement lead time for purchased MRP requirements.
- `OFBIZ-13452`: calendar behavior for backward scheduling should remain separate from this ticket.
